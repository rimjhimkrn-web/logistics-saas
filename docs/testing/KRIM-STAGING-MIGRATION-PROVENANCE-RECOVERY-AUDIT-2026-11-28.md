## Existing repository recovery mechanisms inspected
1. `.github/workflows/krim-schema-export.yml` exports schema-only SQL from the Production database URL secret, encrypts it and publishes a one-day encrypted artifact. This is not a Staging backup and does not include data, Auth users, Storage objects, Vault secrets or provider credentials.
2. `.github/workflows/krim-staging-schema-bootstrap.yml` can apply a validated schema-only artifact to an EMPTY Staging database. It explicitly refuses to proceed if application schemas already contain objects. Current Staging is populated, so this workflow is not a valid repair path for current Staging.
3. `.github/workflows/krim-private-schema-review.yml` and `.github/workflows/krim-schema-manifest.yml` can inspect an encrypted export in an ephemeral GitHub runner and publish sanitized metadata only. They require a valid unexpired artifact and workflow dispatch.
4. The previously identified export artifact (run 44072524850 / artifact 14323377203) is expired. No artifact bytes were retrieved or decrypted in this audit.
5. Connected GitHub tools available in this session provide repository GET/read and file/commit operations, but no workflow_dispatch action or local shell/CLI/Docker runner. The existing workflows therefore cannot be started by this session.

## Safest recovery strategy without an owner-held archive
Do not try to replay 499 files as-is and do not reset Staging.

A controlled forward-only recovery path is:
1. Freeze schema changes while this inventory is reconciled.
2. Export a fresh, schema-only Staging snapshot through an approved ephemeral runner, with no rows, Auth data, Storage objects, secrets or provider credentials.
3. Generate a sanitized manifest and privately retain the exact schema-only artifact with checksums and access control.
4. Reconcile every one of the 163 applied ledger rows against repository SQL using object/function/DDL fingerprints; specifically resolve the 34 unmatched entries and two same-name applied versions.
5. Reconstruct a canonical ordered migration history in a new isolated recovery branch or clean test repository. Preserve original files and checksums; never silently rewrite already-applied migration files.
6. Use a disposable Supabase CLI + Docker environment to test the proposed baseline/replay and subsequent migrations. Compare resulting schema, functions, ACLs, RLS, triggers and Storage policies against the captured Staging manifest.
7. Only after parity is demonstrated, prepare a forward-only Staging migration path with an explicit recovery/rollback plan and owner approval.
8. Treat Production as a separate target with its own ledger/schema comparison and explicit release approval.
